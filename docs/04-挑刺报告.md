# 多智能体需求挑刺报告 —— 决策版

> 生成于 2026-10-15。对《01-需求文档.md v0.3》做的一次**四方独立挑刺 + 主裁决**。
> 方法：同时派出 4 个不同立场的 AI（需求完整性 / 目标用户 / 技术可行性 / 反方风险）并行读文档、互不商量地各自批判，再由人工裁决交叉归并。

## 0. 总裁决（先读这节）

四份挑刺独立出稿，却在**三个点上不约而同地收敛**。凡多方独立命中的问题，几乎必然是真正的病根，按加权处理。

**一句话内核判断**：
> 这份需求文档在"怎么把产品造出来"上已经很成熟（链路、降级、迁移、扣子分支都想到位了），但它**从未正面回答生死问题：一个『怕麻烦的人』凭什么会坚持记账超过 2 周？** 所有验收线都建在"他肯记"的假设之上，却没去验证这个假设本身。**同时，文档存在两处自相矛盾会直接让第一轮真机测试假通过或假失败。**

**三个共识病根**（多个专员独立命中）：
1. **动机 ≠ 省事**（B 用户、D 反方命中）——把"麻烦"等同于点按成本，押注"记录够省事就会坚持"。但历史先例证明：痛的从来不是记的摩擦，是坚持的动机。省事只让尝鲜期更顺，救不了第 3 周的崩。
2. **验收标准是空架子**（A 完整性、D 反方命中）——§4 功能表的"验收"列全是功能复述（"识别→入库→扣预算"），不是可测标准；唯一带数字的验收只挂在 §12.2 扣子分支上，自建/二期无对应判据。
3. **热量/宏量唯一真技术幻想 vs 验收误设**（C 技术命中）——照片识别食堂拼盘，"总热量"勉强 ±20%，但**蛋白宏量根本达不到 ±20%**，文档却把两者捆在同一条验收线，必然触发假失败。

**三个"还没回答的选项"级问题**（影响方向，须你拍板）：
- X1. **可能根本不需要造 / 造太重了**（D 命中）——微信 bot + 一张表单也许已够用；若笨办法留存不输，那 VPS/App/PWA/克数建议/训练达标全套皆多余。
- X2. **合规盲区**（D 命中）——自动算热量线、给克数指令已是"营养处方"，对孕妇/慢病/青少年缺免责与人群排除，个人也担责。
- X3. **2 周验不出留存**（B、D 命中）——第 1 周全勤是"尝新动机"非 product fit，死亡谷在第 3~6 周。

## 1. 需立即修——自相矛盾/错误标态（不修则第一轮测试失真）

### 1.1 验收标准没和"要做的东西"绑定
- **位置**：§4 三张表 vs §12.2
- **问题**：P0 的"验收"列是"识别→入库→扣预算"这类功能复述；真正可测数字只在 §12.2（扣子分支）。自建路线开工时没有"做完"的量化定义，要拍板的正是"F1~F8 一期全做"。
- **改法**：把 §12.2 四个指标抽成**路线无关的 P0 验收模板**（记录坚持率 / 识别误差± / 算账漏记上限 / 界面可接受度），自建与扣子各填执行口径；给 P1/P2 每项补一行"通过线"。

### 1.2 状态谎报：拿未验证的功能去定验收基线
- **位置**：§12.1 vs 03 §4.5
- **问题**：§12.1 把拍照视觉、更正、训练达标、档案记忆全标"✅满足"，但 03（同日生成）白纸黑字"拍照视觉路径/更正/汇总 ⬜ 待测"。违背 README"单一事实源/状态必须更新"纪律。
- **改法**：把 §12.1 满足度拆成"设计满足度 vs 已实测"两态（设计✅/实测⬜），2 周验收只对已实测功能计数。

### 1.3 热量/宏量验收线误设
- **位置**：§12.2、§4 F1、03 §1.4
- **问题**：把"总热量"和"蛋白宏量"捆在同一条验收线（±20%）。拼盘食堂里总热量勉强达标、蛋白基本达不到，必然假失败。
- **改法**：±20% 只对总热量承诺；蛋白宏量单独降标（宽松 ±，或降到"近似"）；把一等准确度押到《常吃食物热量表》+ 更正回流，视觉定位为"粗记 + 触发更正"。

### 1.4 数字前后打架 + "宏量预算"承诺无落地
- **位置**：§3 vs 03 §3 vs §2
- **问题**：热量日目标 1900 vs 2000 混用；正文承诺营养师负责"宏量预算"，但 F1~F5 只谈 kcal 和蛋白，meals 表仅有 protein_g 列，碳水/脂肪无机构无字段。
- **改法**：全文统一一个热量目标（以"按档案算"为准）；明确蛋白默认算法（如体重×系数）；给 meals 表补碳水/脂肪列，或明确"本期只追踪 kcal+蛋白"。

### 1.5 热量来源链自打脸 + 边界未定义
- **位置**：§11/§8.1 vs 03 §1.4
- **问题**：① §11 说不做薄荷级食物库复刻，但 F1/F4/F13 全靠一个覆盖食堂菜的热量表；§8.1 拍板选薄荷而非 OpenFoodFacts，03 §1.4 却用 OFF。② F7 判断"渐进超负荷递增"需跨周历史，workouts 表无序列/周次字段、"本周"切分未定义；补记/跨零点日期归属无规则。
- **改法**：① 明确"不做复刻"= 不做全量餐饮库、只做用户个人常吃表，把热量链统一成一条（本地清单→薄荷查表→LLM兜底），去掉 OFF 标注。② workouts 加周次/排序字段 + 定义递增判定规则（同类动作组次须较上周增）；定义跨零点/补记三条规则；迁移时给表结构映射 + 去重口径。

## 2. 生死问题——建议在烧一分钱功能前先验证

### 2.1 唯一致命假设
> **"一台零摩擦的记热量工具 = 减肥成功"**——赌"记好了自然会减"。证伪动作：把 2 周验的过线从"≥10/14 天有记录"改成**行为结果检验**——比较第 8~14 天 vs 第 1~7 天记录频次衰减率 + 期末体重/腰围是否有可测下降。若第 2 周照样跌，死的是动机不是工具，全案作废/转向。

### 2.2 可能不用造这么重（D 命中，须你拍板）
先花一周用**微信群定时 bot + 每日一题一张表**跑同一批人同一 2 周。若笨办法留存数据不输你的产品，则 VPS/App/PWA/克数建议/训练达标全套都先用不上了——不造就是最大的省事。

### 2.3 合规免责（D 命中，30 分钟成本）必须现在补
档案加排除项（孕妇/慢病/青少年/低 BMI）+ 输出固定免责行"仅面向健康成人，慢病/孕产请遵医嘱"。否则自动热量线=健康处方，个人承担连带责任。

## 3. 技术落地的硬约束（C 命中，改法照守，防账本无声塌方）

1. **求和/日期归属/路由一律走确定性程序节点**，LLM 只做人话→结构化、声明意图绝不自算（03 §1.2 三原则落实：查库、求和、路由不经 LLM）。
2. **账本可观测性**：每次扣账回执必须带"今日已记 N 笔"，否则漏记是无声塌方——把验收从"每周漏/错≤1"提前到这个可观测信号。
3. **目标参数走外部传入（档案/DB）**，绝不让 LLM 去知识库翻 daily_target/protein（知识库=RAG 命中非 100%，翻错→全天预算全错）。
4. **周复盘用确定性聚合（自建 SQL）**，LLM 只做解读不给数。
5. **成本写全**：边际 API（低用量确实 <0.1 元/天）与持有成本（VPS≈1.2~1.5 元/天）分开算；自建 = 7×24 运维义务，配"最低运维清单"（自动备份/systemd 自拉起/证书半自动），做不到就把自建排在扣子后。
6. **识别 API 切换以实测**自家食堂菜目的误识别率为准，别凭品牌比价；杠杆在常吃表覆盖 + 更正回流，不在双供应商。
