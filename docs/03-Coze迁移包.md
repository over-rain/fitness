## 1. 工作流设计模式（平台无关）

### 1.1 结构图（已验证跑通）

```
输入: user_text(用户原话), image_url(可选,照片), daily_target, protein_target
  ↓
① 意图识别 [LLM 节点]
   输入: user_text + image_url
   输出: JSON {intent, parsed{...}}          ← 结构化，不给自由发挥
  ↓
② 意图路由 [程序分支，读 intent 字段]        ← 确定性判断，非 AI
   ├─ 记餐  → 记录餐食 [DB写 + 计算]
   ├─ 记训练 → 记录训练 [DB写 + 估算]
   ├─ 查剩余 → 查询剩余额度 [DB读 + 求和]     ← 全程不经 LLM，杜绝心算错误
   └─ 要调整 → 饮食调整建议 [LLM，对照缺口给1~3条]
  ↓
输出: reply(卡片文本), intent, daily_summary
```

### 1.2 设计三原则（这是最值钱的部分）

1. **AI 负责理解，程序负责正确**：只有"把人话翻译成结构化字段"才用 LLM；查库、求和、路由判断全部用确定性节点。账本不出错靠的就是这条。
2. **路由读字段，不听 LLM 自由发言**：分支条件绑定 `intent` 字段值，LLM 只在提示词约定的枚举里选（记餐/记训练/查剩余/要调整）。
3. **参数外部传入，不写死**：daily_target、protein_target 由调用方（用户档案）传入，提示词和代码里零硬编码。

### 1.3 输出卡片格式（3 行内，已验证）

```
✅ 已记录晚：清蒸鱼1块、米饭1碗、蔬菜1份，约345kcal（区间276~414）｜蛋白26g
👤 邶风｜📊 今日已吃 925/2310 kcal｜蛋白 45/138g
➡️ 剩余 1075 kcal
```

- **👤 身份 + 该人热量线必须每条回执回显**（2026-10-15 补，多用户防记串）：👤 显示的姓名与 📊 里的目标数字必须同属一人（邶风↔2310/138g，gagayouna↔1349/86g）。出现错配 = 身份记串，当场指出并检查当日该 user_id 的全部记录——把无声的账本交叉污染变成肉眼可见的事故。这不是权限，是可校验的回执。

### 1.4 热量来源降级链（可拔插设计）

```
① 查《常吃食物热量表》(本地知识库/表)   → 命中: 权威值, 标 [表]
② 未命中且为包装食品 → OpenFoodFacts   → 命中: 标 [OFF]   (试验期可暂不实现)
③ 仍未命中 → LLM 凭经验估              → 给区间, 标 [估], 提示可更正
```

- 原则：LLM 估算只做兜底，不做一等来源（一致性漂移会毁掉汇总趋势）
- **来源必须写入记录的 note 字段**（[表]/[OFF]/[估]），周复盘可审计；用户更正 [估] 记录时将更正值沉淀进表（表的成长机制）
- 智能体线实现 = 提示词规则；编程线/自建实现 = `resolve_kcal(food) -> (kcal, source)` 优先级循环
- 试验期只实现 ①+③；② 等真的开始记包装食品再加，防过度设计

### 1.5 实测性能基准（参考）

| 环节 | 耗时 |
|---|---|
| 意图识别（LLM，冷启动） | ~4.8s；热态 ~1s |
| 意图路由（程序） | ~5ms |
| 记录入库（DB 写） | ~270ms |
| 全链路单次 | ~5s（冷）/ ~1.3s（热） |

## 2. 提示词资产

### 2.1 意图识别提示词模板

```
请识别以下减肥管家用户输入：
文字: {user_text}
图片URL: {image_url if image_url else '（无）'}

# 任务目标
判断用户输入的意图类别，并尽可能解析出结构化字段，供后续记账与计算使用。

# 意图枚举（四选一）
记餐 / 记训练 / 查剩余 / 要调整

# 输出
严格输出符合契约的 JSON 结构。
```

> ⚠️ 待补全：这是从运行记录反推的骨架。**完整提示词请从扣子意图识别节点里复制**（含字段枚举、few-shot、JSON schema 约束），贴到 `2.1 完整版` 小节。

### 2.2 输出 JSON 契约（实测样例）

```json
{ "intent": "记餐", "parsed": { "items": ["清蒸鱼1块","米饭1碗","蔬菜1份"] } }
```

### 2.3 更正规则（提示词内必须写死，防止重复记账）

```
# 更正规则
- 用户说"更正/不对/搞错了/其实是…"时：
  1. 定位目标：今天（或用户指定日期）最近一条该餐次的记录
  2. 修改该条记录的字段，禁止新增重复记录
  3. 回复格式：✅ 已更正：{新食物}，约{新热量}kcal
- 用户删除某笔记录同理：定位 → 移除 → 确认
```

**v2 补充（2026-10-16，本地版实测踩坑）**：裸描述式更正（上条"咖啡"，用户只说"燕麦拿铁"）不会被关键词规则命中，会被当新记录造成重复。修法：把**今日已有记录**（id/餐次/食物/kcal）作为上下文喂给模型，让它在输出 JSON 里自判 `action:"record"|"correct"+id`，服务端按 id 原地改写；id 无效则降级为新增。另：思考型模型（glm-5.3-flash）可能把 max_tokens 全花在思考上导致正文为空，需 3000+ tokens 且空正文自动重试一次。

### 2.4 身份识别规则（多用户，A 简化版）

```
# 身份规则（两人共用本管家）
- 会话开始或首次记餐/记训练前，若不知道用户身份，先问一句：
  "你是邶风还是 gagayouna？"（确认后本会话内不再问）
- 后续所有记录 user_id 用确认的身份；汇总/剩余额度按该用户的档案目标计算
  （邶风 2310kcal/蛋白138g；gagayouna 1349kcal/蛋白86g，见知识库《身体档案》）
- 不做任何数据隔离：两人记录同库，只按 user_id 取各自目标
- 回执强制回显「👤 身份｜📊 已吃/该人目标」（见 §1.3）：身份与目标数字错配即记串，当场更正（2026-10-15 补）
```

### 2.5 人设提示词（智能体线整段）

见《02-扣子搭建指南.md》第 2 节，叠加 §2.3 更正规则块和 §2.4 身份规则块使用。

## 3. 数据表结构

### meals（餐食账本）

| 字段 | 类型 | 说明 |
|---|---|---|
| user_id | String | 用户标识（beifeng / gagayouna），选档案用 |
| id | Integer | 记录ID（自增） |
| date | String | YYYY-MM-DD |
| meal_type | String | 早餐/午餐/晚餐/加餐 |
| food | String | 菜品内容 |
| kcal / kcal_low / kcal_high | Integer | 热量中值/下限/上限 |
| protein_g | Integer | 蛋白克数 |
| note | String | 备注/用户更正 |

### workouts（训练账本）

| 字段 | 类型 | 说明 |
|---|---|---|
| user_id | String | 用户标识（beifeng / gagayouna），选档案用 |
| id | Integer | 记录ID |
| date | String | 日期 |
| action | String | 动作 |
| sets_reps | String | 组次（如 4x12） |
| duration_min | Integer | 时长（分钟） |
| est_kcal | Integer | 估算消耗 |
| note | String | 备注 |

> 目标参数（daily_target / protein_target）不进这两张表，放用户档案（`data/profiles/*.json`），调用时传入。
>
> **多用户（已拍板 2026-10-15，A 简化版）**：单智能体服务 2 人（邶风/gagayouna），两张表**首列均加 `user_id | String | 用户标识（beifeng / gagayouna）`**，作用仅一个：查当日汇总和写记录时选对热量档案。**不做数据隔离/权限**（用户已确认互见无所谓）。配套身份识别规则见 §2.4。

## 4. 平台经验教训（扣子，2026-10 时点）

1. **积分机制**：建设期烧"与编程 AI 对话"积分（调试循环是大头）；运行期每次 LLM/视觉调用都烧积分，**视觉识别是最贵的一步**。项目积分预算上限务必设置（当保险丝）。
2. **预览 ≠ 部署**：IDE 里的 devbox 预览能跑，不代表已部署服务可用；停服（积分用尽）后手机端直接不可用。验证链路可以趁预览免费推进。
3. **两条产品线**：编程线（code.coze.cn，功能强但积分付费，且 2026-09-08 起停止新建）；智能体线（coze.cn 智能体编辑页，自带数据库+工作流，个人轻度使用基本免费额度内）。选型结论见《01-需求文档.md》§12.3。
4. **导出**：平台 DSL 导出（zip/JSON）只在扣子生态内可用，无跨平台通用格式。**真正的迁移包 = 本文档 + 数据库 CSV/JSON 定期备份**。
5. **验收进度**（2026-10-15）：记餐链路 ✅ 已验证；更正/汇总/拍照视觉路径 ⬜ 待测。
