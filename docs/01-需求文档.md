# 个人减肥管家 —— 需求文档 v0.3（定位定稿版）

> 变更摘要（v0.2 → v0.3）：
> ① 产品定位升级为「**怕麻烦的人的减肥管家**」——管家 + 营养师 + 健身教练三合一；② 核心机制确定为**热量预算制**（日目标 − 已吃 = 剩余，随时问"还能吃多少"）；③ 记录方式定为**一步式**：拍照 或 说句话，无表单无弹窗；④ 新增**克数级饮食建议**（多少米饭/多少肉/多少菜）；⑤ 新增**训练达标判断**与**计划导入/导出**；⑥ 部署锁定**公网 VPS**（有网络就能用）；⑦ "语音"方案定为手机输入法语音转文字（零开发成本）。

---

## 1. 一句话定位

一个手机网页（PWA）：**吃饭前/后拍一张或说一句话 → 自动记录并扣减今日热量预算 → 随时告诉你"还能吃多少、建议怎么吃"；训练说一句话 → 自动记录、判断今天练没练到位；每周自动复盘、改进计划，支持导入网上热门计划、导出自己的框架。** 全程为一个目标服务：减肥。

## 2. 产品角色（语气与职责）

| 角色 | 职责 | 输出风格 |
|---|---|---|
| **管家** | 替你记一切：吃了什么、练了什么、剩多少额度 | 你只管"拍照/说话"，其余全自动 |
| **营养师** | 热量/宏量预算、餐盘克数建议、外食选择建议 | 短、可执行（"米饭150g+鸡腿1个+青菜随意"，不写论文） |
| **教练** | 训练计划管理、动作指导、达标判断、渐进超负荷 | 直接说"今天缺什么、明天怎么补" |

**设计铁律（怕麻烦三原则）**：
1. **一步记录**——任何记录动作 ≤ 1 步（拍照发出去 / 说一句话），无表单、无确认弹窗、无必填项
2. **卡片反馈**——分析结果 ≤ 3 行卡片（剩余额度 + 建议），长分析只在你主动问时展开
3. **有问必答但不主动刷屏**——平时安静，你问"要不要调整"才给建议

## 3. 核心机制：热量预算制（产品骨架）

```
日目标 1900 kcal（按档案自动算，减肥缺口 −350~500）
  = 早餐 450 + 午餐 650 + 晚餐 600 + 加餐 200   ← 餐次预算可自动分配也可手动调
每记录一餐 → 扣减对应预算
任何时刻可问：「晚上还能吃多少？」→ 立刻回答：剩 620 kcal
```

- 记录早/午/晚后，**主动显示**"今日剩余"，不用问也知道
- 超支/结余都有明确提示（"午餐超了 150，晚餐建议减主食"）

## 4. 功能需求

### P0（一期，核心闭环）

| 编号 | 功能 | 说明 / 验收 |
|---|---|---|
| F1 | **拍照记餐** | 拍餐盘→视觉模型识别菜品+份量→估热量/宏量→自动入账扣预算。识别结果可一键改（怕识别错） |
| F2 | **说话记餐** | 语音转文字（用手机输入法自带语音，零开发）→"我早上吃了两个包子一杯豆浆"→文本解析→自动入账。拍照不便/零食加餐用这个 |
| F3 | **剩余额度查询** | 首页常显「今日剩余 X kcal / 已吃 Y / 目标 Z」；提问"晚上还能吃多少"秒答 |
| F4 | **克数级饮食建议** | 剩余额度 → 换算成具体建议：「晚上：米饭 150g + 瘦肉 100g + 蔬菜 300g（约 580 kcal）」。外食场景给"选这个别选那个"式建议 |
| F5 | **饮食调整问答** | "我吃的要不要调整？"→ 对比当日目标给 1~3 条具体调整（减半碗饭 / 加个蛋补蛋白） |
| F6 | **说话记训练** | "今天练了深蹲 5x5、卧推 5x5，50 分钟"→ 记录动作/组次/时长 + 估消耗（区间） |
| F7 | **训练达标判断** | 对照本周计划框架："今天练到位了吗？"→ 答：练了哪些、缺哪块（如"今天缺推类，明天补卧推"）、渐进超负荷是否递增 |
| F8 | **档案与目标** | 身高/体重/年龄/性别/目标体重/周练几天/现有计划框架。初始化问一次，之后永不忘（存数据库）；每日热量线自动算 |

### P1（二期）

| 编号 | 功能 | 说明 |
|---|---|---|
| F9 | **计划导入** | 粘贴文字/截图网上热门计划（如谭chengyi 等）→ 视觉/文本模型结构化 → 转成我的周计划框架（可再手工微调） |
| F10 | **计划导出** | 导出我的「饮食框架 + 训练框架」：Markdown（人看/存档）+ CSV（丢给 AI 分析）+ 长图（分享）。框架可简可繁 |
| F11 | **周复盘 + 计划改进** | 每周汇总：摄入超支几天、训练达标率、体重变化 → 给下周计划的具体修改建议 |
| F12 | **体重打卡趋势** | 一句话"今早 66.5"→ 记录 → 曲线 + 与目标差距推算 |
| F16 | **健康线提醒（吃太少预警）** | 当日已吃 < 健康线（= max(本人 BMR, 女1200/男1500)，按档案自动算）时，当日回复给 1 条提醒：低于健康线会掉肌肉、降代谢、越减越难减、易暴食反弹，女性可能月经紊乱；口径是"保护这次减肥"，非指责式。验收：低于线必现、≤1 行、同日不重复刷屏；高于线永不出现 |

### P2（暂缓）

| 编号 | 功能 |
|---|---|
| F13 | 常吃食物库（识别过的固化，一键复用，越用越准） |
| F14 | 定时提醒（晚上没记录晚餐时轻轻提一句） |
| F15 | 多端数据同步到微信/邮件周报 |

## 5. 场景剧本（一天的真实使用，验收基准）

> **早上 7:30**（食堂）拍一张 → 卡片：`早餐 ~480 kcal｜蛋白 18g｜今日剩余 1420`
> **上午 10:00** 说句"喝了一杯拿铁" → `+180 kcal｜剩余 1240`
> **中午 12:00** 拍一张 → `午餐 ~610 kcal｜剩余 630`（若超预算：`午餐超 80，晚餐建议少吃主食`）
> **下午 15:00** 问"我吃的要不要调整？" → `蛋白偏低(38g)，晚餐建议加鸡腿或鸡蛋×2；主食已够，菜多饭少`
> **下午 17:00** 问"晚上还能吃多少？" → `剩 630 kcal ≈ 米饭150g + 瘦肉120g + 蔬菜300g + 一个苹果`
> **晚上 20:00** 说"练了深蹲4组12个、弓步蹲3组、桌沿划船3组，40分钟" → `已记录✓ 消耗约 220~280 kcal｜对照本周计划：✅腿+拉完成，今日达标`
> **周五晚** 问"这周怎么样？" → 周复盘卡片 + 下周调整建议

## 6. 技术方案（AI 辅助开发，不锁语言）

| 层 | 选型 | 要点 |
|---|---|---|
| 前端 | 手机优先单页 Web + PWA（加到主屏像 App） | 拍照 `input capture`；语音=输入法转文字，前端只需文本框 |
| 后端 | 轻量栈任选（FastAPI / Node / Spring，AI 开发都快） | 接口：上传照片、文本解析、查询剩余、训练记录、计划 CRUD、导出 |
| 识别引擎 | **多模态大模型 API，做成可切换配置**（DeepSeek-Vision / GLM-4V / 通义，默认 DeepSeek） | 拍照识别 + 文本解析 + 周复盘分析共用 |
| 数据 | SQLite（单文件）+ 照片目录 | 表：profile / meals / workouts / plans / weights |
| 部署 | **公网 VPS + Docker + Caddy 自动 HTTPS** | HTTPS 必须（手机摄像头权限要求）；域名解析到 VPS，出门在外照常用 |

## 7. 架构链路

```
手机 PWA（拍照/说话/提问）
   │ HTTPS
   ▼
VPS 后端 ──存 SQLite──► 预算引擎（日目标-已吃=剩余）
   │
   ├─ 照片 ──► 多模态API(可切换) ──► 菜品+份量+宏量(区间) ──► 入账
   ├─ 文本 ──► 大模型解析 ──► 食物/动作结构化 ──► 入账
   └─ 查询 ──► 剩余额度 / 克数建议 / 达标判断 / 周复盘
```

## 8. 参考（不重复造轮子）

wger（训练+营养数据模型参考）、openGym（渐进超负荷可视化思路）、exercises-dataset（动作库数据）、OpenFoodFacts（营养兜底）；成品 App（Strong=训练交互标杆、薄荷=营养库标杆）仅作交互参考。

### 8.1 竞品结论（2026-10-15 调研）

按核心需求五条（聊天式/可更正/账本可靠/免电脑/免费）对照：商业拍照记餐 App（Cal AI、SnapCalorie 等）账本可靠但订阅付费、中餐弱；直接聊大模型免费但无真账本；开源自托管（wger/mealie/Tandoor）需服务器，与"免电脑"冲突。**结论：无现成品全满足，扣子智能体线为唯一同时满足五条的路径**——支撑 §12 分支方案。另：热量数据源选薄荷 App 而非 OpenFoodFacts/mealie（食堂菜覆盖与录入成本原因），详见《03-Coze迁移包.md》。

## 9. 非功能

| 项 | 要求 |
|---|---|
| 隐私 | 数据在自己 VPS；照片仅发给识别 API，不落第三方 |
| 无广告 | 零广告零推荐流 |
| 成本 | VPS ~20-40 元/月 + 模型 API 按量（一天拍照+解析 < 0.1 元级） |
| 诚实性 | 识别/消耗一律给区间+依据；估算≠精确 |
| 抗丢失 | SQLite 定时备份；记录只追加不删改 |

## 10. 已定决策 & 仅剩拍板项

**已由你本轮输入决定**：✅ 公网部署（有网络就能用）；✅ 拍照+说话双记录；✅ 热量预算制；✅ 克数建议；✅ 训练达标判断；✅ 计划导入导出；✅ 不做 App/小程序；✅ 语音用输入法转文字；✅ 用户 2 人（邶风/gagayouna，档案与热量线见 `data/profiles/`，2026-10-15 按 Mifflin-St Jeor 算定：2310/1349 kcal）；✅ 多用户落法：**单智能体 + user_id 简化版**（user_id 仅用于选对热量档案，不做数据隔离/权限，2026-10-15 拍板，理由：使用最简单——一个链接两人用，互见数据无所谓）；✅ 健康线提醒 F16（2026-10-15：吃太少不利于减肥本身——掉肌肉/降代谢/易暴食/女性月经紊乱，低于健康线时主动提醒；放 P1 但实现极简，可随 F3 预算查询顺手做）；✅ 试验期功能优先级：**拍照记餐+剩余额度先行，训练记录暂缓**（2026-10-15，智能体线 v1 只建 meals 表）。

**仅剩 2 个**：
1. **识别 API 默认用哪家**？（建议 DeepSeek-Vision 起步、GLM-4V 备用，配置可切换——你两家额度都有）
2. **P0 范围 F1~F8 一期全做**，确认？（约等于：先把"吃"的闭环做穿，训练记录同期能用，导入导出放二期）

## 11. 明确不做

原生 App / 小程序 / 薄荷级食物库复刻 / 精确到克称重级精度 / 医疗建议 / 聊天型通用助手功能（只做减肥管家该做的）。

## 12. 分支方案：扣子先行（2 周试验，2026-10 起）

> 主线（第 6~7 节自建）**不变**。先用扣子类工具把「记录习惯 + 需求」验证 2 周，不满意/不满足则回到自建。搭建细节见同目录《02-扣子搭建指南.md》。

### 12.1 扣子分支覆盖的功能

| v0.3 功能 | 扣子分支实现 | 满足度 |
|---|---|---|
| F1 拍照记餐 | 聊天框发图 + 视觉模型识别 + 数据库入库 | ✅ |
| F2 说话记餐 | 输入法语音转文字 → 文本解析入库 | ✅ |
| F3 剩余额度查询 | 数据库查询 + 工作流计算（可靠度依赖工作流） | ⚠️ 可用但非 100% 稳 |
| F4 克数建议 | 人设提示词 + 常吃食物热量表知识库 | ✅ |
| F5 调整问答 | 人设提示词 | ✅ |
| F6/F7 训练记录+达标 | 数据库 + 训练计划知识库 | ✅ |
| F8 档案记忆 | 知识库 + 变量 | ✅（核心痛点解决） |
| 显示界面 | ❌ 聊天流，无仪表盘卡片 | ❌ 与自建的差距点 |
| 数据私有 | ❌ 存扣子平台 | ❌ 与自建的差距点 |

### 12.2 2 周验收标准（2026-10-13 起跑，10-27 复盘）

| 指标 | 通过线 |
|---|---|
| 记录坚持 | ≥ 10/14 天有真实记录 |
| 识别准度 | 误差 ±20% 内可接受，离谱错误 < 1/3 餐 |
| 算账可靠性 | 漏记/日期错 ≤ 每周 1 次 |
| 界面 | 聊天流可长期接受 |

**任一不通过 → 启动自建**（记录从扣子数据库导出 CSV 迁移，无缝衔接）。

### 12.3 产品选型结论

首选 **扣子国内版（coze.cn）**：数据库+工作流是同类里唯一能撑起"记账"的；备选腾讯元器（微信生态但结构化弱）；Dify/FastGPT 属"半自建"（数据私有，仍聊天界面），作为中间态备胎。
